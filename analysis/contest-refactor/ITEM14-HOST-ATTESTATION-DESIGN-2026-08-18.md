# Item 14 — Host-Attestation Design: The Execution-Evidence Ledger (2026-08-18)

## Verdict: buildable today as a same-privilege wrapper; not buildable today as strict
## host attestation, on any of this skill's five harnesses

All five harnesses this skill supports (`references/provider-adapters.md`) ship a real,
host-fired hook or plugin system that runs outside the model's *content* authorship: Claude
Code and Codex CLI both have documented `PreToolUse`/`PostToolUse` hooks, Gemini CLI has
`BeforeTool`/`AfterTool`, GitHub Copilot CLI has `preToolUse`/`postToolUse`, and OpenCode has
`tool.execute.before`/`tool.execute.after`. That much genuinely helps: for a real Bash-tool
invocation, the exit code / stdout / stderr a hook receives is generated by the harness's own
tool executor before the model ever sees it, so the model cannot make that specific field say
something the real subprocess didn't return.

But that is a narrower guarantee than "host-attested," and the gap document is explicit that the
weaker guarantee is not enough (`docs/review-skill-deep-dive-2026-08-17.md:598-599`: *"an
'append-only' file the model can write — or delete and recreate — is not independent evidence...
an instruction does not authenticate a file"*). In every one of the five harnesses' documented
configurations, the hook or plugin runs as **the same OS user as the agent's own shell tool
calls** — I found no harness where the hook process is privilege-separated from the agent
process. That means a model that specifically sets out to defeat the design can, in every case
I verified, write or append a hand-crafted record in the exact shape the real wrapper would have
produced, using the exact same file permissions the wrapper needs to do its own job. Two
harnesses (Claude Code, GitHub Copilot CLI) ship an **enterprise/policy-level** config layer
that would close this — genuinely outside the agent's write reach under normal OS permissions —
but both require an organizational deployment (MDM-managed settings, or a `policy.d` file an
admin drops with `sudo`) that this repo does not have and that a typical solo `/contest-refactor`
user is unlikely to set up. **This repo has zero hook configuration today, for any harness**
(verified: no `.codex/`, `.gemini/`, `.opencode/` directories exist; there is no `.claude/settings.json` at all — only `.claude/settings.local.json`, which has
no `hooks` key; `.github/` has only `workflows/`, no `hooks/`).

The one piece of directly-relevant prior art vendored in this repo — `gstack-evidence`
(`refs/competitors/contest-refactor/gstack/bin/gstack-evidence`) — confirms this is not a
gap in my research but the actual state of the art: it is a **transparent same-privilege
wrapper**, not a privilege-separated attester, and its own sibling tool `gstack-verify-gate`
states its trust model out loud: *"hooks bypass the permission system"* is offered as the
reason a **human** must run a separate `--trust` step to hash-pin the command before the hook
is allowed to block anything (`gstack-verify-gate:11-17`). Nothing in the corpus this skill has
already surveyed does better than that.

So the honest scope for this pass: build the **Tier-1** control (a wrapper that is the true
parent process of the test/build command, records what it directly observed, and is pinned
against a human-established canonical command) as a real, valuable anti-fabrication control
against the everyday failure mode named in the gap — a loop that reports a passing build it
never ran, or reports the wrong run's result. Do **not** claim it defeats a deliberately
adversarial model that reverse-engineers the ledger format; that requires a privilege-separated
writer (**Tier 2**) that nothing in this repo or its competitor corpus has built. Section 4
proposes the field that keeps this honest in the shipped artifact, not just in this doc.

## Scope note

Design note only, per the assignment. No canon, gate, schema, or code changes ship in this pass.
Every claim about a harness's current behavior below carries a citation — either a `file:line`
into this repo or its vendored competitor corpus, or a fetched vendor-documentation URL. Where a
claim could not be settled from a primary source in the time available, it is marked
**uncertain**, with what would settle it, rather than asserted.

## 1. The trust boundary, stated precisely

**The load-bearing rule, applied without softening:** a hook *config file* or *plugin file*
sitting inside the git-tracked project tree — `.claude/settings.json`, `<repo>/.codex/hooks.json`,
`.opencode/plugins/*.js`, project `.gemini/settings.json`, `.github/hooks/*.json` — is a file the
model's own Edit/Write/Bash tools can reach under normal permissions. A prose rule telling the
loop not to touch it is not a boundary (this is exactly the class of control the gap document
rejects). The only configurations below that count as attestation boundaries are the ones sitting
**outside** that reach: a user-home-directory location the operator (not the loop) populates once,
or a genuine OS-policy location requiring elevated privileges to write.

| Harness | Hook/plugin mechanism (verified) | Config locations found | Real exit code in payload? | Protected/policy-level location? | This repo today |
|---|---|---|---|---|---|
| Claude Code | `PreToolUse`/`PostToolUse`, `settings.json` | Project `.claude/settings.json` (agent-writable); user `~/.claude/settings.json`; **managed settings** (admin/MDM, `allowManagedHooksOnly` blocks all non-managed hooks) | **Yes** — Bash `tool_response` carries `exit_code`, `stdout`, `stderr`, `interrupted` (confirmed via search of Claude Code hooks docs) | **Yes, but enterprise-only** | No hooks configured — no `.claude/settings.json` exists; `.claude/settings.local.json` carries only `permissions`/`skillOverrides`/`enabledPlugins` |

**Per-harness verdict:**

- **Claude Code**: hook mechanism is real and its exit-code payload is the most concretely
  confirmed of the five. It is **not** an attestation boundary as this repo is configured today
  (no hooks defined). It *could* become one at the managed-settings tier, but that tier is an
  MDM/enterprise deployment concept, not something `/contest-refactor`'s own installation
  (symlink into `~/.claude/skills/`, per this repo's `CLAUDE.md`) can turn on for a solo user.
  First-party confirmation that the hook layer itself is privilege-distinct from ordinary
  permissions comes from this exact competitor corpus, not just vendor docs:
  `gstack-verify-gate:11` states plainly *"hooks bypass the permission system"* — which is why
  that tool requires a separate human `--trust` action before it lets a hook block anything.
- **Codex CLI**: hook mechanism exists (`PreToolUse`/`PostToolUse`, CLI v0.117.0+) but I could not
  confirm the payload includes a verifiable raw exit code, and found no policy-only config tier.
  **No attestation boundary found** — the user-level `~/.codex/hooks.json` location is outside
  the repo (a real, if modest, improvement over project-local config) but nothing prevents the
  same OS user from editing it, and no enterprise-lockout mechanism analogous to Claude Code's
  `allowManagedHooksOnly` was found.
- **OpenCode**: weakest of the five by construction — its hook mechanism is a **loadable JS/TS
  plugin**, i.e. arbitrary code the same session could also write, rather than a declarative
  config file a hook runner merely reads. **No attestation boundary found.**
- **Gemini CLI / Antigravity CLI**: hook mechanism exists in Gemini CLI's own docs; Antigravity
  publishes a separate hooks page (`antigravity.google/docs/hooks`) I did not fetch, so whether
  it is the same mechanism is **uncertain: fetch that page and diff against Gemini CLI's schema
  before assuming parity**. No protected location found in either. **No attestation boundary
  found**, pending that check.
- **GitHub Copilot CLI**: the only harness with a documented **filesystem-policy** location
  (`/etc/github-copilot/policy.d/`) that is admin-only under default OS permissions **without**
  needing an enterprise console — genuinely the strongest candidate. But I could not confirm from
  the fetched reference that a repo-level `.github/hooks/*.json` hook is *disabled* in the
  presence of a policy one (the docs describe load *priority*, not exclusivity), so I cannot
  currently state that policy.d is a complete lockout rather than merely a highest-priority
  layer that a project-level hook could still run alongside. **Promising, not yet verified.**
- **`unknown`**: no subagent spawn at all in this mode (`references/provider-adapters.md:92-96`)
  — there is no host process to fire a hook, so this is trivially **no attestation boundary
  found**, same conclusion the design already reaches for `loop_model: null` under this provider.

**The real axis is not "which harness has a hook named `PostToolUse`."** Every harness above
that has one still runs it under the agent's own OS user. The property that actually matters —
can the *writer of the ledger record* act with privileges the agent's own shell does not have —
is a **Tier 1 vs Tier 2** question that is largely harness-independent:

- **Tier 1 (buildable now, everywhere):** a wrapper script this skill ships is the literal parent
  process of the test/build command (`subprocess.run`/`Bun.spawn`, not a reported value), so the
  exit code it records cannot be a claim — it is the real child's `wait(2)` result. This defeats
  *lazy* fabrication (claiming a result without invoking anything) and *wrong-result* reporting
  (claiming pass when the wrapper's own record says fail), and needs no harness-specific hook at
  all — it works identically on every harness, including `unknown`, because the model itself
  invokes it via the ordinary shell tool. It does **not** defeat a model that skips the wrapper
  and hand-writes a same-shaped record, because the wrapper and the model's shell share the same
  file-write privilege.
- **Tier 2 (not built anywhere in this corpus):** a privilege-separated writer — a local
  daemon/socket service or setuid helper, started by the operator before the session, that alone
  can append to the ledger, with the agent only able to submit an execution *request* over a
  channel it cannot also use to inject an arbitrary already-computed record. This is the only
  configuration that defeats a model that specifically studies the ledger format and forges a
  same-privilege append. I can name the shape of this mechanism; I cannot point to an existing
  implementation of it in this repo or its competitor corpus, including `gstack-evidence` itself.

## 2. The record schema

Modeled on `gstack-evidence`'s shipped fields (`{ts, label, command, cmd_sha256, exit,
duration_s, commit, tree, dirty, wtree, log_path, redacted}`,
`refs/competitors/contest-refactor/gstack/bin/gstack-evidence:43-54`), adapted to what this
skill's gates need to bind and check.

| Field | Binds | Defeats |
|---|---|---|
| `run_id` | the loop/invocation this record belongs to | a record from a different, unrelated invocation being cited as if it were this one |
| `command` + `command_sha256` | the exact string executed | citing a *different* command than the one a human pinned as canonical (see below) |
| `cwd` | where it ran | a record produced against the wrong checkout/worktree |
| `wtree` (working-tree **content** fingerprint, not `git rev-parse HEAD`) | the exact code under test, including uncommitted and untracked changes | **the replay attack**: this skill's own existing `source_rev` field is HEAD's sha at emit time (`references/output-format-json.md:126`) — but Step 3's fix is uncommitted until sub-step 11 (`SKILL.md:191-230`), so HEAD does not move during the loop that matters most. A record bound only to HEAD sha would let a passing run from *before* the fix be replayed as evidence *for* the fix, because HEAD is identical in both cases. `gstack-wtree` exists precisely to solve this: it stages the full working tree (`git add -A` into a throwaway index) and prints `git write-tree`, so committing identical content doesn't change the fingerprint but an untracked new file or an edit does (`refs/competitors/contest-refactor/gstack/bin/gstack-wtree:1-13`). **This repo has no equivalent primitive today** — `candidate_fingerprint.py` hashes the *review JSON's* architecture-relevant payload, not git tree content, and the deep-dive itself notes the two serve different purposes (`docs/review-skill-deep-dive-2026-08-17.md:685`). A `wtree`-equivalent is new work this item must add, not something to reuse from `source_rev`. |
| `timestamp` | when it ran, from the wrapper's own process clock | the model backdating/forging recency; not model-suppliable since the wrapper reads its own clock |
| `exit_status` / `signal` | what the child actually returned, via `wait(2)`/`proc.returncode`, not a reported value | the mismatched-exit-code RED case (§5) — the model's prose claim can be checked against a value it did not author |
| `output_digest` (sha256 of stdout+stderr; raw output **redacted**, never stored durable) | that *some* output existed and can be compared against a later independent re-hash if ever needed | a record whose command ran but whose actual output is silently swapped for something else after the fact; matches this repo's own no-durable-raw-output convention this session has applied elsewhere (item 25's row explicitly inherits "no durable raw tool output" from items 1/3/18, `docs/review-skill-deep-dive-2026-08-17.md:1153`) |
| `attestation_status` | which trust tier produced this record | see §4 — this is the field that keeps a Tier-1-only deployment honest in the artifact itself |

Two fields I considered and cut: a **hostname/machine identifier** — `gstack-evidence` deliberately
keeps its ledger machine-local rather than syncing it (*"neither the ledger nor the logs are
brain-synced. A synced record citing an unsynced log would grade FRESH on a machine where the log
doesn't exist,"* `gstack-evidence:26-28`) — but this skill's loop already runs single-machine
per invocation, so a hostname field would name an attack (record-transplanted-across-machines)
this design doesn't need to defend against yet; add it only if the loop ever runs distributed.
And a **duration** field — useful for humans, but I could not name a forgery it defeats on its
own (a model padding a fabricated duration doesn't get past the exit-code and wtree checks
either way), so it's cut per the brief's own instruction to cut fields nobody can name an attack
for.

**The command-binding precondition.** Binding `command_sha256` only defeats forgery if the value
it's checked against was **pinned by a human, not declared by the model at Step 0/1 of the same
loop it's meant to constrain** — otherwise the model is both the author of "the canonical command"
and the value being validated against it, which authenticates nothing (the same rule as §1,
applied to a canon entry instead of a hook config file). `gstack-verify-gate` solves exactly this
with an explicit one-time `--trust` action a human runs out-of-band, storing `path → sha256(command)`
in `~/.gstack/verify-gate-trust`, invalidated the moment the declared command changes
(`gstack-verify-gate:9-17`). This design should adopt the same shape: a human-run one-time
trust-pin step, not a model-self-declared canon value.

## 3. The linkage gate

**What G4 already requires.** `references/validation.md:40`: *"every score above 7 has at least
one source-backed reason in the final text... Suspended for any scorecard entry with
`unverifiable_due_to_build_failure: true`."* G4 is a **presence-and-shape** check on the
artifact's own prose — it asks whether a score has *a* citation, and (via the build-failure
suspension) already assumes the model's own claim about whether the build passed or failed is
the ground truth being cited. G4 does not, and structurally cannot, ask whether that citation
corresponds to anything that actually happened outside the model.

**What the new gate adds — precisely, and no more.** Call it G47 (the next free ID at the time of
writing per `canon/validation-gates.toml`; re-verify before implementing, since multiple items are
landing gates in this same session and G46 was claimed mid-session by item 28's work). The
artifact's Step 1 / Step 3 test-run citation carries an `event_id` referencing a ledger record;
the gate:

1. **Resolves** the record by `event_id` — missing ⇒ fail (the "missing record" RED case).
2. **Checks `record.command_sha256` against the human-pinned trust store** — mismatch ⇒ fail (the
   "wrapped a different command" attack named in §5, not one of the gap's original four but
   constructible against a naive command-string check).
3. **Recomputes `wtree` fresh, right now, and compares it to `record.wtree`** — not merely "is
   `record.wtree` present," but "does it equal the *current* working tree." This is what actually
   closes the replay case: a record is valid evidence for *this* diff only while the diff is
   unchanged since the record was made.
4. **Checks `record.exit_status == 0`** (or whatever the artifact's own prose claims — a record
   that says `exit_status: 1` cited as proof of a passing build is a distinct, catchable
   dishonesty, separate from missing/forged).
5. **Reads `attestation_status`** and requires it be present and truthful per §4's coupling rule.

What this gate **cannot** conclude, stated as plainly as the brief asks: it cannot conclude the
*command itself* is semantically the right test suite (only that it matches what a human pinned
once); it cannot conclude the record wasn't hand-forged by a model with matching file privilege
(Tier 1 has no defense against that — see §5); and it cannot conclude anything at all when
`attestation_status` is honestly `unavailable` — at that point it is exactly as blind as G4 is
today, by design, per §4.

**Non-duplication of G4.** G4 stays exactly as it is — a score still needs a source-backed prose
reason. G47 is additive and strictly narrower: it only fires on the specific citation that claims
a ledger-backed run, and only checks the four mechanical properties above. A loop that never
claims ledger backing (because no wrapper was used, or `attestation_status: unavailable`) is not
touched by G47 at all; it is still governed by G4 alone, same as today.

## 4. The honest downgrade

This is the section the brief calls the most important one, and this repo has already shipped
the same class of honesty mechanism three times this session — the new field must follow their
pattern, not invent a fourth shape:

- **Item 21** (`[[project_contest_refactor_principal_plan]]`-adjacent trial-validity taxonomy):
  `historical_validity()` reads a record's own `trial_validity` key and returns `"not_recorded"`
  — **never** `"valid"` — when the key is absent or malformed, with the function's own docstring
  stating the rule it exists to prevent: code that would otherwise do
  `record.get("trial_validity", {}).get("status", "valid")`-shaped defaulting *"would silently
  promote absence to validity"* (`scripts/_trial_validity.py:127-136`).
- **Item 20** (noise-floor gate): `evaluate_lift()` returns `status="unreportable"` — never a
  fabricated `floor=0` — when no measured noise ceiling exists for the matched key
  (`scripts/_noise_floor.py:37,392,403,410`); the canon's own comment states the principle
  directly: *"absence of that measurement makes a claim unreportable regardless of this constant
  (D6)"* (`canon/noise-floor.toml:40-42`).
- **Item 17** (`HALT_EXHAUSTION`): G45's *"honesty coupling is the point of the gate"* —
  `detection_mode == "preventive_step_budget"` **forces** `kind == "unknown"`, because a
  step-budget checkpoint genuinely cannot distinguish context pressure from a spend limit from
  any other cause, and only a `user_reported` detection may name a specific one
  (`references/validation.md:215-221`; `canon/exhaustion-kinds.toml:11-14,16-22`). The same file
  also declines to ship a `host_meter` token *ahead of a real producer*, with the comment stating
  why: *"shipping the vocabulary ahead of a producer is dead enum"* (`canon/exhaustion-kinds.toml:26-28`)
  — directly on point for this item, which likewise has no Tier-2 producer to back a stronger
  claim than Tier 1 today.

**Proposed field, following the same shape:** `attestation_status ∈ {"attested", "consistency_check",
"unavailable"}`, required whenever a Step 1/Step 3 citation references an `event_id` (per §3), with
a coupling rule mirroring G45's: a record is legally `"attested"` **only** when the record was
written by a mechanism verified privilege-separated from the agent (Tier 2) — since this pass
builds no such mechanism, **no record produced by this design may claim `"attested"` today**; the
canon should not even enumerate a route to it until a Tier-2 writer exists, exactly as
`exhaustion-kinds.toml` withholds `host_meter`. Every record this pass can actually produce is
`"consistency_check"`: same-privilege wrapper, real exit code, wtree-bound, human-pinned command —
genuinely useful, honestly labeled as *not* immune to a deliberate forger. `"unavailable"` is the
correct value whenever no wrapper was invoked at all (harness offers nothing, or the loop skipped
it) — the artifact then reads exactly as it does today, G4-only, no ledger claim made.

This has to be **visible in the emitted artifact text**, not just carried in JSON a human never
reads — otherwise, per the brief, "a consistency check silently reads as attestation." Concretely:
the Step 1/Step 3 result prose should read *"build verified via consistency-check ledger (event
`<id>`); this control does not defend against a model that forges a matching record"* rather than
a bare citation that could be mistaken for a stronger claim. The exact wording is an
`output-format` decision for the implementation pass, not this note, but the **non-claim must ship
in the sentence the model writes**, the same way G45's handoff template makes the "cannot tell
context pressure from a spend limit" limitation part of the user-facing text
(`references/halt-handoff.md:437`) rather than leaving it as an internal comment.

## 5. The adversarial RED cases

| # | Attack | Caught by this design? | Mechanism |
|---|---|---|---|
| 1 | **Missing record** — artifact cites `event_id` that resolves to nothing | **Yes** | G47 step 1, fail closed |
| 2 | **Forged record** — model hand-writes/appends a ledger line in the exact shape the wrapper produces, without ever invoking it | **No, not at Tier 1** | The wrapper and the model's own shell share file-write privilege in every harness surveyed (§1). This is the residual risk this note names explicitly rather than papering over; only a Tier-2 privilege-separated writer closes it |
| 3 | **Replayed record from an earlier run** — a genuine, unforged record from *before* the fix, cited as if it validates the fix | **Yes, if bound to `wtree` recomputed fresh at gate time; No, if implemented against the existing `source_rev` (HEAD sha) instead** | HEAD does not move during Step 3 until the final commit (`SKILL.md:191-230`), so a HEAD-only binding is defeated trivially; this is precisely why §2 requires a new working-tree-content fingerprint field, not a reuse of `source_rev` |
| 4 | **Mismatched exit code** — record says `exit_status: 1`, artifact prose claims the build passed | **Yes** | G47 step 4; `exit_status` is the wrapper's own `wait(2)`/`proc.returncode` result, not a model-reported value |
| 5 | **Wrapped a trivial/no-op command** (`-- true`) to generate a legitimately-attested-but-meaningless record | **Yes, if `command_sha256` is checked against a human-pinned trust store; No, if checked against a model-self-declared canon value** | §2's command-binding precondition — a self-declared "canonical command" authenticates nothing, same rule as §1 applied to canon instead of a hook config |
| 6 | **Direct out-of-band invocation of the wrapper/hook script itself** with hand-crafted stdin, mimicking a genuine harness dispatch | **No** | Every harness's hook and the model's own shell run at the same OS privilege (§1); nothing in any of the five harnesses' documented payload schemas includes a harness-held secret the model cannot also read or reconstruct. This is a distinct failure mode from #2 (forging the *ledger file* directly) — here the *wrapper itself* is tricked into legitimately writing a record for fabricated inputs |
| 7 | **Working-tree edit during the run** — code changes *while* the test command is still executing, so the recorded `wtree` doesn't reflect what actually ran | **Partially** — `gstack-evidence` fingerprints `wtree` **before** spawning the child specifically to avoid certifying content the suite never ran (`gstack-evidence:186-188`, `:297,302` degrades to STALE on a mid-run change); this design should do the same. But a change made *after* completion and *before* commit is a distinct case, closed only by G47 step 3's requirement to recompute `wtree` fresh at gate/commit time rather than trusting the record's own snapshot as final |
| 8 | **Append-only protection was never actually set up** — the operator skipped the one-time root-privileged `chattr +a`/`chflags schg` step, so Tier 1 quietly loses even its rewrite/delete protection | **Not caught by the gate at all — this is exactly why `attestation_status` cannot silently upgrade based on intent.** The field records only what tier the *record-writing mechanism* verifiably is, and this design does not currently include a way to *verify* the append-only flag is actually set (a gap worth naming: a preflight check that stats the ledger file's flags and refuses to label anything `"consistency_check"` if the file is trivially rewritable would strengthen this, and is cheap to add — but is not designed in this pass) |
| 9 | **Clock forgery** — model claims a more favorable timestamp than what actually happened | **Yes** | `timestamp` is the wrapper's own process clock, not model-suppliable |
| 10 | **Symlink swap / TOCTOU on the ledger path** — replace the ledger file with a symlink to attacker-controlled content between the wrapper's write and the gate's read | **Uncertain** — none of the five harnesses' hook docs I fetched, nor `gstack-evidence`'s own source, address this; it would need to be verified against whatever OS/filesystem the operator actually deploys on, and is out of scope to resolve here |

**Stated plainly, per the brief's own demand for honesty about coverage:** this design defeats
the *lazy* and *self-deceived* fabrication case the gap's own framing centers on — *"a loop that
reports a passing build it never ran"* — because at minimum it forces the model to either invoke
the real wrapper (giving a true record) or leave `attestation_status: unavailable` (giving no
stronger claim than exists today). It does **not** defeat a model that has read this design and
specifically sets out to forge a matching record with matching file privilege (#2, #6). Closing
that requires Tier 2, which nothing in this repo or its competitor corpus has built.

## 6. Cost, sequencing, and what to build first

**Smallest genuinely-attesting increment.** A single wrapper script (e.g.
`scripts/attested_run.py`, modeled directly on `gstack-evidence`'s `cmdRun` — spawn the real
child, stream+tee output to a capped/redacted log, record `{run_id, command, command_sha256, cwd,
wtree, timestamp, exit_status, signal, output_digest, attestation_status: "consistency_check"}` —
plus a `wtree`-equivalent primitive (`git add -A` into a throwaway index, `git write-tree`,
matching `gstack-wtree`'s approach) this repo does not currently have. It needs **no harness-
specific hook integration at all** — the model invokes it via the ordinary shell tool on every

   ceiling this pass should target, not a floor to improve past.

   working-tree content fingerprint (this repo's existing `source_rev` is HEAD-sha-only and
