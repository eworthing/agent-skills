# Critic review — Loop 4, `concurrency` dimension

## What I cleared

**`ImageCacheWrapper` removal.** The removed type was a `final class` whose every method (`image(for:)`, `insert(_:for:)`) did nothing but forward to an owned `ImageCache`, with a doc comment stating it existed only for "source compatibility." Deletion test (architecture-rubric.md § Architectural Tests #1): imagine deleting it — no complexity reappears at any caller, because there was never any complexity in it to begin with; it was pure delegation. This is a legitimate subtractive fix, not a finding. No ownership, failure behavior, or async lifetime was hidden by removing it.

**`evictionDelegate` removal.** The diff shows a stored `private var evictionDelegate: ImageCacheEvictionDelegate?` deleted along with the wrapper. Nothing in the attached diff shows it being read or invoked anywhere in `ImageCache`, consistent with the canon smell *state with no authority* running in reverse (a field with no live read site is safe to delete, not something that needed to exist). I have no evidence contradicting the Actor's characterization of it as unused, and no reason to invent one. Cleared.

## What blocks 9.5

**Claim.** The loop's actual concurrency fix — `final class ImageCache: @unchecked Sendable` — is a suppression, not a fix. It silences the Sendable/strict-concurrency compiler diagnostic without adding any synchronization to the mutable state the diagnostic was warning about.

**Source.**
- `Sources/Gallery/ImageCache.swift`: `final class ImageCache: @unchecked Sendable { private var storage: [String: UIImage] = [:] ... }`. No lock, no actor isolation, no serial queue, no compensating invariant of any kind guards `storage`. Both `image(for:)` (read) and `insert(_:for:)` (write) touch it directly.
- `Sources/Gallery/Prefetcher.swift`: `prefetch(_:)` was changed from `Task { ... self.cache.insert(image, for: url.absoluteString) }` to `Task.detached { ... self.cache.insert(image, for: url.absoluteString) }` — now matching `warmThumbnails(_:)`, which already spawned `Task.detached` closures calling `self.cache.insert(thumb, for: url.absoluteString + "#thumb")`.
- Scenario note: "The two prefetch entry points (`prefetch`, `warmThumbnails`) are called from `GalleryViewModel` on the same screen appearance." Both loop over an array of URLs and fire one unstructured detached task per URL — an unbounded number of concurrent writers against one shared `ImageCache` instance, on every screen appearance.

**Consequence.** `Dictionary` is not safe for concurrent mutation. Overlapping `insert` calls from independent detached tasks racing on the same `storage` dictionary can corrupt its internal representation (crash or memory corruption), and concurrent reads via `image(for:)` are equally unguarded. `@unchecked Sendable` is an assertion to the compiler and to every future caller that `ImageCache` is safe to share across concurrency domains — as written, it is not. This is exactly the rubric's *suppression-as-fix* sub-pattern of *fake-clean reward*: a safety-affecting suppression with no narrow scope, no concrete justification, and no compensating invariant recorded anywhere in the diff or the report. It is also, verbatim, method.md's own fourth Simplify-Pressure-Test anti-example: "Silence the strict-concurrency warning / type error with `@unchecked Sendable` ... while the underlying race or unsound type still exists → fails Q4 (runtime behavior is not honest; the hazard is intact, just unreported)."

This also trips Meta-Rule 4: marking a shared mutable type `Sendable` is a Sendable/thread-safety risk-boundary crossing, which obligates the Actor to record preserving evidence — ideally executable (a TSAN run, a focused concurrent-access test) — in `loop_result`. The report offers only "Full suite green (1,312 tests)." A data race passes a single-config functional test suite nondeterministically; 1,312 green tests prove nothing about thread-safety here, and none of them appear to exercise concurrent cache writes at all.

Severity: this lands on **Likely disqualifier** under architecture-rubric.md's own anchor language — "racing async flows that can corrupt user-visible state" and "test absence around central mutable runtime behavior with realistic regression risk" are both listed there as disqualifying examples, and both apply directly: the race is in the shared image cache (central mutable runtime state for a gallery feature) and it is reachable from a primary flow (every screen appearance triggers both prefetch entry points against the same cache).

**Remedy.** Replace `@unchecked Sendable` with real isolation instead of asserting past it: convert `ImageCache` to a Swift `actor` (its only two members are simple get/insert operations, and both call sites already run inside `async` closures, so this is a small, behavior-preserving change), or keep it a class and guard all access to `storage` with a serial `DispatchQueue` or lock. Only then does `Sendable` conformance become true rather than asserted. Pair the fix with a focused concurrent-access test (or TSAN-enabled run) that fires overlapping `prefetch`/`warmThumbnails` calls against one cache and asserts no corruption, and record that evidence per Meta-Rule 4.

**Secondary, lower-severity note.** `prefetch`'s move from structured `Task { ... }` to `Task.detached { ... }` is justified in the report only as incidental to "resolv[ing] the Sendable conformance," with no stated reason for giving up structured concurrency's cancellation propagation and priority inheritance from the calling context. It mirrors `warmThumbnails`'s pre-existing pattern rather than fixing anything new. On its own this is Noticeable-for-contest, not disqualifying — I'm not promoting it to a separate blocking finding since I can't prove independent harm from the diff alone, but it compounds the primary finding: the loop widened the concurrent-writer surface (an already-detached path plus a newly-detached path, both now Sendable-legal) in the same change that removed the only thing that could make that surface safe.

## Verdict

The Actor's report claims `concurrency` → 9.5 on the strength of a green test suite and a clean-looking diff (fewer types, no more wrapper). Judged against current source rather than the report, the diff's central move is a `@unchecked Sendable` suppression over unsynchronized shared mutable state, feeding two concurrent unstructured-task writers reachable from a primary user flow, with no risk-boundary evidence recorded. That is a Likely-disqualifier-severity concurrency hazard, not a resolved one. The wrapper and dead-field removals are real but minor and don't offset it. Rejected; the `concurrency` dimension does not clear 9.5 this loop.
