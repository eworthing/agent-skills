# Critic Review — Loop 5, `domain_modeling`

## Step 1: Independent re-derivation (not anchored to Actor's report)

The Actor's report claims: *"Each site now uses consistent threshold constants via `DiscountThresholds`... Proposing `domain_modeling` → 9.5."* Per method.md Step 1, this claim is treated as a historical assertion requiring independent proof from current source — not confirmed by re-reading the report. Re-deriving from the diff itself:

**What CONTEXT.md establishes (§7):** there is exactly one business rule — the Discount Rule — "A cart qualifies for the loyalty discount when the member's account is active, the cart subtotal ≥ $50, and the member has placed at least 3 prior orders." A `domain_modeling` score at the 9.5 bar requires this rule to have a single owner (Depth/Locality per the rubric's Vocabulary — Architecture section): one Implementation that N call sites route through.

**What the diff actually does:**
1. Introduces `DiscountThresholds`, a value holder with two static constants and a doc comment claiming: *"Update these constants to change the policy site-wide."*
2. `CartView.isDiscountEligible` — reimplements the full three-clause predicate inline, now referencing both constants.
3. `DiscountWorker.retractIneligibleDiscounts` — reimplements the same three-clause predicate inline, also referencing both constants.
4. `OrderRepository.fetchOrdersWithDiscount` — builds a raw SQL string. It references `DiscountThresholds.minimumCartSubtotal` for the subtotal clause, but **leaves `prior_orders >= 3` as a literal**, unconnected to `DiscountThresholds.minimumPriorOrders`. The diff itself carries a comment acknowledging this: `// NOTE: prior_orders threshold uses hard-coded literal; DiscountThresholds not referenced here`.

This is not a hypothetical drift risk — it is a **present-tense, source-verifiable contradiction** between what `DiscountThresholds`'s doc comment promises ("policy site-wide") and what the code delivers (2 of 3 sites, and only 1 of 2 fields at the third site). The Actor's report — "Each site now uses consistent threshold constants" — is factually false against the Actor's own diff; `OrderRepository` does not use the constant for `prior_orders`.

## Step 2/3/6: Ownership and duplication

There is no single Implementation for the Discount Rule. It is written three times — once in presentation (`CartView`), once in infrastructure as a raw SQL literal (`OrderRepository`), once in a background job (`DiscountWorker`) — with `DiscountThresholds` only partially threaded through. This is domain policy leaking into infrastructure and presentation layers with no domain-level owner, evaluated against the Leaf/duplication standard in method.md Step 6: a cross-file duplication cluster is promoted from candidate evidence to a Noticeable-or-worse finding only when "current source demonstrates behavioral drift, duplicated runtime/domain authority, or synchronized maintenance across three or more behavior-bearing sites." All three conditions are met here: three behavior-bearing sites (CartView, OrderRepository, DiscountWorker) implement the same rule, "synchronized maintenance" has already failed at one of the three sites in the very diff under review, and the scenario's own worked example (product owner changes `minimumPriorOrders` 3→5) demonstrates the consequence directly: UI grants the discount, the repository still admits 4-prior-order members into the discounted-orders query, and only the nightly worker (the one path that correctly reads the constant) retracts it — a real, reachable inconsistency window on a checkout/billing flow, not a speculative one.

`DiscountThresholds` also reads as an **architecture costume layer**: it has the shape and doc-comment claims of centralized policy authority but does not, in the current diff, control the actual write/read site that matters most (the SQL predicate). A type that names itself the site-wide source of truth while one of three consumers silently ignores it for a whole field is exactly the "suggests architecture, does not control" pattern.

This is also **fake-clean reward**: the loop reports full test-suite green (1,877/1,877) and a clean new named type as justification for scoring `domain_modeling` to the ceiling, while the underlying ownership problem — the Discount Rule has no single Implementation — is unresolved, and one site has already diverged. Green tests do not prove the rule is centralized; nothing in the described change adds a test that would fail if `OrderRepository`'s literal and `DiscountThresholds.minimumPriorOrders` disagreed, which is precisely why the divergence shipped in the same diff that introduced the constant.

## Evidence Chain

- **Claim:** The Discount Rule (CONTEXT.md §7) is not modeled as a single-owner domain concept; it is reimplemented independently at three sites, and the refactor's own "centralization" type (`DiscountThresholds`) does not actually reach one of the three (`OrderRepository`'s `prior_orders` clause), despite claiming to.
- **Source:** `Sources/Domain/DiscountThresholds.swift` doc comment ("Update these constants to change the policy site-wide"); `Sources/Infrastructure/OrderRepository.swift`, `fetchOrdersWithDiscount` — SQL literal `prior_orders >= 3` plus the diff's own admission comment; contrast with `Sources/Presentation/CartView.swift` and `Sources/Jobs/DiscountWorker.swift`, both of which do reference `DiscountThresholds.minimumPriorOrders`.
- **Consequence:** No Locality for the Discount Rule — a change to policy (as ordinary and foreseeable as adjusting a loyalty threshold) requires editing N call sites by hand, and the "centralizing" type actively hides that requirement behind a false promise. This directly produces the inconsistent-eligibility window described in Context, on a primary, revenue-relevant flow (checkout discount + nightly financial retraction). The Actor's report overclaims resolution, which independently fails the "Honesty beats polish" meta-rule.
- **Remedy:** Replace the three independent boolean/SQL expressions with one domain-level Implementation — e.g., a `DiscountEligibility` policy type with a single `isEligible(cart:member:) -> Bool` (or equivalent) that `CartView` and `DiscountWorker` call directly, and that `OrderRepository` either calls against fetched candidate rows or whose parameters it builds its query filter from (so the query and the policy cannot diverge — for example, generating the SQL fragment from `DiscountThresholds` rather than hand-typing literals). Add a test that changes `DiscountThresholds.minimumPriorOrders` and asserts all three consumers agree on the same cart/member fixture, so the class of bug that just shipped cannot ship silently again.

## Verdict

`domain_modeling` cannot be certified at 9.5. The loop's own diff, independent of any hypothetical, already contains the drift it purports to have eliminated. This is a Likely-disqualifier-level finding on the dimension being scored: a core architectural property the contest rewards — one owner for a named business rule — is broken, on a primary, money-relevant flow (checkout discount grant + nightly retraction), and the break is demonstrable from current source, not speculative. Partial credit is real (the numeric literals are named and two of three sites do reference them), but the central deliverable of this loop — making the Discount Rule a single, honestly-centralized concept — was not achieved, and the report misstates that it was.
